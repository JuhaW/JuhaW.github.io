See what your project actually contains — and colour it the way you think about it.

FreeBASIC Panel builds a live map of a FreeBASIC project: every function, every type, every variable, and every library your code pulls in. It shows you what is there, what depends on what, and which parts of the project the work is concentrated in.

On top of that map you can organise your symbols into colour groups you name yourself. A symbol belongs to a group, the group has a colour, and that colour follows the symbol everywhere it appears — in the editor, in the hover card, and in the sidebar.

The sidebar

One panel along the side of the editor, six views into the project.

Functions

Everything you can call, gathered under its colour group. See who calls what, jump straight to any definition, and mark the handful of functions you keep coming back to as favourites.

Types

Your own types and enumerations, opened up into the variables of that type and the functions that belong to it.

Groups

Where the colour groups live. Create them, rename them, recolour them, reorder them by dragging, or switch one off without losing it.

Files

The modules in your project and the libraries they include. Library files can be given a group of their own, so code you did not write reads differently from code you did — without opening or editing them.

Analysis

Where the activity is. Which files carry most of the work, and which symbols the rest of the project leans on.

Settings

Everything configurable in one place: how much colour, how much emphasis, where your FreeBASIC lives, and who you are annotating as.

Narrowing down

The lists are big, because real projects are. You can cut them down to the file you currently have open, or to the files actually visible on screen — so the panel answers "what is here right now" instead of "what exists somewhere".

When a list comes up empty, it says why: nothing in this file, nothing matching your search, nothing in this category. A blank list with no explanation is worse than no list.

Colour groups

Most editors give a file one keyword colour, and that is the whole idea. This one starts somewhere else: the project is divided into named groups, and each group has one colour.

Call them whatever fits — Library, Own code, Interface, Needs review. The name is yours; it is not tied to any part of the language.

Assign once, follow everywhere

Put a symbol in a group once. It takes that colour in the code, in its hover card and in the sidebar. Nothing has to be kept in step afterwards.

Group a block, or single out one symbol

A group is inherited by everything inside it, so assigning a whole block is one action rather than hundreds. But any individual symbol can step out and join a different group — one function in a library block can be moved into your own group without being lifted out of the block it lives in.

Turning things off without losing them

A group can be disabled. It stops colouring and leaves the sidebar, but it is still there, and switching it back on brings the arrangement back with it.

Nothing falls through the cracks

Symbols you have not grouped yet are gathered into one holding group, kept in a fixed position so the list never quietly reshuffles under you. It is also how you find out what is still unaccounted for.

Several people, one codebase

Groups, colours and favourites belong to a person, not to the project file. Everyone annotating the same code gets their own view, and nobody overwrites anybody else. Switch identity in the panel; add more people when you need to.

In the editor

Hover tells you the useful thing

Hover any symbol to see what it is, which group it belongs to, and who uses it. You can move it to a different group straight from the hover card, without leaving the file you are reading.

Resolving follows scope

A local variable that shadows a module-level one of the same name is a real problem in every language. Here, hover, colouring and group changes all follow scope, so they describe the symbol you are actually pointing at — the inner one — rather than the first name match in the file.

Structure you can see

Group membership tints your code, and function blocks are marked out so a long routine has a visible shape instead of running off the screen. How much of both you see is up to you.

Your regulars, marked

The functions you marked as favourites are starred beside the code, so the two or three you actually work with are findable at a glance in a file you have not opened in months.

Overloads resolve out loud

When a project uses overloaded functions, the editor works out which one your call binds to, and shows you. Literals, variables, expressions and object properties are all taken into account, instead of leaving you to work it out from the parameter list.

Problems, minus the noise

Unresolved names are reported — but the ones coming from FreeBASIC's own headers are filtered away, and library code is not held against you. What you are shown is meant to be yours to fix.
