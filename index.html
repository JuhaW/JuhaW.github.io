Take control of your FreeBASIC project

FreeBASIC Panel brings the automation and clarity of a modern development environment straight into VS Code. It removes the two things that eat your time in multi-module FreeBASIC projects: copy-pasted Declare lines that never stay in sync, and library includes you have to keep guessing at.

What problems does this solve?

Growing FreeBASIC projects hit the same handful of walls over and over.

❌

The usual way

  • Copying Declare lines from file to file, by hand, forever.
  • Calls that break the moment you reorder your modules.
  • Guessing how a library like BASS, SDL3 or Cairo wants to be declared.
✨

With FreeBASIC Panel

  • Fully automatic: every module-level function and sub gets its declaration written for you.
  • Order stops mattering: every module sees every other module's signatures, so a call no longer fails just because of file order.
  • Type accuracy: parameter types are copied from the definition rather than retyped — so a call that should bind to one overload binds to that one.
🎯

The result

  • You write application logic instead of bookkeeping.
  • Renaming or moving a function needs no follow-up edits anywhere.
  • The whole project builds in one command.

Colour groups

Most editors give a file one keyword colour. This one lets you invent your own.

01

Make a group

Give it a name and pick a colour from the picker. Call them whatever fits your project — Library, Own code, Interface, Needs review. Turn one off whenever you want; it keeps its place and its members.

02

Put things in it

Functions, subs, types and enums all go into groups. Move one at a time from the list or straight from its hover card, or put a whole category in at once when you want every type — or every instance — grouped together.

03

It shows up in the code

The symbol takes the group's colour in the editor straight away, and keeps the same colour everywhere else it appears. Nothing has to be kept in step by hand afterwards.

◐

An instance can differ from its type

An instance of a type does not have to follow the type's colour. Put the instance in its own group and it takes that colour instead — useful when one variable of a type matters to you and the rest do not.

◑

Fall back, do not blank out

An instance with no group of its own takes its type's colour, and a type with no group stays a neutral grey. So nothing ever disappears just because you have not classified it yet.

◇

Ungrouped is a real group

Everything you have not put anywhere lands in a holding group, kept in a fixed place so the list never reshuffles under you. It is also the quickest way to see what is still unaccounted for.

How it takes the work off your plate

What the tool does in the background, while you get on with the actual code.

01

Declarations, generated

The extension reads your modules and collects every module-level function and sub. That list is written to a single file which the compiler is told to read first, so no module ever calls something the compiler has not been told about.

02

Libraries without the guesswork

Include lines are listed in the Files view, where you can see at a glance what your project pulls in and give library code a colour of its own. Point the extension at your FreeBASIC installation and the header libraries behind those includes are recognised too — so a type name coming from a header is not reported as an unknown symbol.

03

One command to build

However many modules the project has, the checked files go to the compiler in a single invocation with the generated declarations ahead of the file names. The compiler's own output is shown unchanged.

What the files look like

Your own code stays untouched. The generated file lives beside it.

Colour groups

You name the groups. A symbol belongs to one, the group has one colour, and that colour follows the symbol into the editor, into its hover card and into the panel. Assign a symbol once — there is nothing to keep in step afterwards.

Groups are yours to name: Library, Own code, Interface, Needs review. Nothing is tied to any part of the language.

Creating a group

  1. Open the Groups tab in the panel.
  2. Press the + button. A form opens with a name field, a colour swatch that already holds a colour, and two buttons. The swatch is a button too — you do not have to accept the colour you are given.
  3. Click the swatch. The colour picker opens: a Saturation slider, and a grid of colours drawn at that saturation. Click a colour and the swatch takes it.
  4. Type a name and press Add. Until the name is filled in, Add stays greyed out. If the name is already in use, the form says so and refuses — you never end up with two groups of one name.

Choosing the colour

The picker works in HSL: the slider sets how strong the colour is, the grid sets the hue and how light it is. Move the slider and the whole grid redraws, so you can walk from muted to vivid without leaving the picker. To change a group that already exists, click its colour square in the list — the same picker opens.

What it looks like

One function, one new group. The same screen twice — the panel on the left, the source on the right.

Inherited groups

A group is inherited by everything inside it, so tagging a whole block is one action rather than hundreds. But any individual symbol can step out and join a different group — one function inside a library block can move into your own group without being lifted out of the block it lives in.

A group can be switched off without being deleted. It stops colouring and leaves the panel, but it is still there.

Instance colours

An instance of a type does not have to follow the type's colour. Put the instance in its own group and it takes that colour instead — useful when one variable of a type matters to you and the rest do not.

Nothing disappears if you have not classified it. An instance with no group takes its type's colour; a type with no group stays a neutral grey.

The six views

Functions — everything callable, grouped by colour, with callers and callees per symbol. Types — your types and enums, opened into their instances and members. Groups — where the colour groups are created, renamed, recoloured, reordered and switched off. Files — the modules in the project and the libraries they include. Analysis — which files carry the work and which symbols everything leans on. Settings — everything configurable, which is also where the panel opens.

Scope filter

The lists are big, because real projects are. Cut them down to the file you have open, or to the files actually visible on screen, so the panel answers "what is here right now" instead of "what exists somewhere".

When a list comes up empty it says why: nothing in this file, nothing matching your search, nothing in this category. A blank list with no explanation is worse than no list.

Hover

Hovering a symbol shows what it is, which group it belongs to, and who uses it. You can move the symbol to a different group straight from the hover card, without leaving the file you are reading.

Resolving follows scope. If a local variable shadows a module-level one of the same name, hover, colouring and group changes all describe the symbol you are actually pointing at.

Overload resolution

When a project uses overloaded functions, the editor works out which one your call binds to and shows you. Literals, local and module-level variables, expression results, conversion functions, type aliases and object member calls are all taken into account.

Without that, the answer would just be the first definition in the list — which is wrong exactly when the definitions are in a different order from what you expected.

Favourites

Mark the functions you keep coming back to. They are starred beside the code in the editor, so the two or three you actually work with are findable at a glance in a file you have not opened in months.

The star can sit in the editor gutter, in the overview ruler beside the scrollbar, in both, or nowhere.

Diagnostics

Unresolved names are reported — but the ones coming from FreeBASIC's own header libraries are filtered away, and library code is not held against you. Point the extension at your FreeBASIC installation and the headers behind your includes are recognised too, so a type name that lives in a header is not an unknown symbol.

What reaches you is meant to be yours to fix.
