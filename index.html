A structured view of a FreeBASIC project, and colour groups you control from the editor.

FreeBASIC Panel gives .bas projects a project-wide view of what is actually in them: which functions exist, where they are defined, what calls them, which types have instances, and which #include lines pull in what.

On top of that it adds colour groups — you assign a symbol to a named group with a colour, and the symbol takes that colour everywhere it appears: in the code, in hover cards, and in the sidebar. Groups can be inherited, overridden per symbol, or switched off without deleting anything.

version 0.0.1 · activates on .bas files · built against FreeBASIC 1.20.0

The panel

The extension lives in the activity bar as a single webview with six tabs.

Functions

Every function, sub and macro in the project, grouped by colour group. Callers and callees per symbol. Scope filter, search, category filter, favourites and drag-and-drop ordering of the groups themselves.

Types

User-defined types and enums, expandable into their instances and members. Members are labelled by kind — method, property, field — and instances show their own colour, falling back to the type's colour.

Groups

The colour groups themselves: name, colour, and whether the group is in use. Groups can be renamed, recoloured, disabled, or dragged to a new position in the sidebar.

Files

The project's .bas modules and its #include lines. Include lines can be marked external and assigned to a group so library code is coloured without being edited. Also generates generated.bi.

Analysis

Cross-reference and heatmap views over the project: which files are busy, and which symbols are referenced from where.

Settings

Editor settings, decoration colours and opacities, identity management, and the FreeBASIC installation folder. This is the tab the panel opens on.

Colour groups

This is the part that has no equivalent in other FreeBASIC tooling. Instead of one keyword colour for the whole file, the project is divided into named groups, and each group has one colour.

Groups are declared in your configuration with an @define directive. The three numbers are H, S, L — hue, saturation and lightness — and the editor converts them to a colour itself:

'@define 0 Library 210, 60, 55
'@define 1 Own Code 120, 76, 51
'@define 2 UI code 30, 30, 30

Inheritance and overrides

A symbol with no group of its own inherits the colour of the group that owns it. A symbol can also carry its own group tag, which overrides the surrounding group — so one symbol in a library block can be moved into Own Code without being lifted out of its block.

Symbols with no group at all land in a reserved Ungrouped group, which is always sorted last so the list order stays predictable. Disabling a group hides it without deleting it.

Scope awareness

Group resolution follows scope. If a local variable shadows a module-level one of the same name, hover, colouring and group assignment all resolve to the one you are actually pointing at — the inner one — rather than the first name match found in the file.

Several annotators, one codebase

Groups, colours and favourites are stored per identity, and every marker written into your code carries that identity. Several people can annotate the same codebase without overwriting each other. The userId setting chooses which identity you are; you create further ones from Settings.

In the editor

Hover

Hovering a symbol shows its kind, name and group on the first line, followed by callers, type and scope information. From a hover card you can move the symbol to a different group without leaving the file.

Decorations

  • A highlight for code lines that belong to a tag group — colour and opacity are settings.
  • A background bar across the whole line of a function block, and separate lines at its top and bottom, each with its own opacity.
  • A star in the editor gutter marking a favourite, optionally also in the overview ruler beside the scrollbar.

Diagnostics

The server reports unresolved calls, but suppresses the ones that are not your fault: symbols that come from the FreeBASIC header libraries, and library code that is not part of your project. What reaches you is meant to be actionable.

Overload resolution

When a project uses overloaded functions, the server resolves the call against the argument types — literals, local and module-level variables, expression results, conversion functions, type aliases, and object member calls — and tells you which definition the call actually binds to.

Compile and run

The compile command builds the checked files in one fbc invocation, passing -include generated.bi ahead of the file names, and shows the compiler's own output unchanged.

freebasic.favourites.decorations "gutter" Where the favourite star appears: gutter, overview, all or none.

Architecture

The project is two programs that talk JSON-RPC over stdio.

  • The extension is TypeScript. It owns the LSP client, the sidebar webview, hover cards, jump targets, decorations and settings.
  • The language server is VB.NET with a Tree-sitter FreeBASIC grammar. It does the parsing and all colour computation, and returns decorations rather than hard-coding them in the client.

Keeping colour decisions on the server side means the same rules apply to decorations, hovers and sidebar rows — they cannot drift apart, because there is only one implementation of each rule.

The generated.bi mechanism follows the FreeBASIC compiler's own -include flag: the server writes a declare line for every module-level function and sub, and the compile command passes that one file before the module names, so every module sees every signature.
