🚀 Stop maintaining declaration headers by hand

Take control of your FreeBASIC project

FreeBASIC Panel brings the automation and clarity of a modern development environment straight into VS Code. You put functions into groups by your own semantics, and every name and call site is drawn in that group's colour. It also removes the chore that eats your time in multi-module FreeBASIC projects: copy-pasted Declare lines that never stay in sync.

Get it from GitHub See what it does

What problems does this solve?

Growing FreeBASIC projects hit the same handful of walls over and over.

❌

The usual way

  • Copying Declare lines from file to file, by hand, forever.
  • Calls that break the moment you reorder your modules.
  • Guessing how a library like BASS, SDL3 or Cairo wants to be declared.
✨

With FreeBASIC Panel

  • Fully automatic: every module-level function and sub gets its declaration written for you.
  • Order stops mattering: every module sees every other module's signatures, so a call no longer fails just because of file order.
  • Type accuracy: parameter types are copied from the definition rather than retyped — so a call that should bind to one overload binds to that one.
🎯

The result

  • You write application logic instead of bookkeeping.
  • Renaming or moving a function needs no follow-up edits anywhere.
  • The whole project builds in one command.

Colour groups

Most editors give a file one keyword colour. This one lets you invent your own.

That is the whole point: you tell the panel which parts of the project matter to you, and those are the parts that get a colour. Not the other way round — a syntax highlighter paints every keyword the language defines, which says nothing about your project. Which code is yours, which came from a library, what is finished and what is still open: that is the thing worth colouring.

And the grouping is yours to define: if five functions belong together in your project — by whatever logic matters to you — put them in one group and their names, along with every place you call them, are drawn in that group's colour. That is semantics you defined yourself; the language knows nothing about it.

01

Make a group

Give it a name and pick a colour from the picker. Call them whatever fits your project — Library, Own_code, Interface, Needs_review. Turn one off whenever you want; it keeps its place and its members.

02

Put things in it

Functions, subs, types and enums all go into groups. Move one at a time from the list or straight from its hover card, or put a whole category in at once when you want every type — or every instance — grouped together.

03

It shows up in the code

The symbol takes the group's colour in the editor straight away, and keeps the same colour everywhere else it appears. Nothing has to be kept in step by hand afterwards.

◐

An instance can differ from its type

An instance of a type or an enum does not have to follow the colour of the group its type is in. Put the instance in its own group and it takes that colour instead — useful when one variable of a type matters to you and the rest do not.

◑

Fall back, do not blank out

An instance with no group of its own takes the colour of the group its type is in. If the type is in no group either, the type and its ungrouped instances are drawn in the editor's normal text colour. So nothing ever disappears just because you have not classified it yet.

◇

Ungrouped is a real group

Everything you have not put anywhere lands in a holding group, kept in a fixed place so the list never reshuffles under you. It is also the quickest way to see what is still unaccounted for.

How it takes the work off your plate

What the tool does in the background, while you get on with the actual code.

01

Declarations, generated

The extension reads your modules and collects every module-level function and sub. That list is written to a single file which the compiler is told to read first, so no module ever calls something the compiler has not been told about.

02

Libraries without the guesswork

Include lines are listed in the Files view, where you can see at a glance what your project pulls in and give library code a colour of its own. Point the extension at your FreeBASIC installation and the header libraries behind those includes are recognised too — so a type name coming from a header is not reported as an unknown symbol.

03

One command to build

However many modules the project has, the checked files go to the compiler in a single invocation with the generated declarations ahead of the file names. The compiler's own output is shown unchanged.

What the files look like

Your own code stays untouched. The generated file lives beside it.

Your module — includes stay here

' Includes belong in your code
#include once "bass.bi"

' No declarations needed
subway(100)
Dim tulos As Integer = ApuSumma(5)

The build command

# Generated file first, output flag last
fbc -include generated.bi 01_kirjasto.bas 02_apumoduuli.bas -x peli.exe

What you can do with it

Build & automation

  • Never write a Declare line again. Every module-level function and sub is declared for you, in one file.
  • Stop caring about file order. Every module sees every other module's signatures, so moving a file cannot break a call.
  • Build the whole project in one command. Every checked module goes to the compiler in a single invocation.
  • Choose what gets built, and in what order. The Files tab ticks modules in and out and orders them by dragging.

Colour & organisation

  • Colour the project your way. Invent groups and put symbols in them; the colour follows the symbol into the editor, the panel and the hover card.
  • Colour one instance differently. An instance can have a group of its own instead of following its type.
  • Tag a type once. Its instances inherit the group, and the Types view marks them as inherited rather than owned.
  • Keep a group through a rename. A group is a tag in an ordinary comment, so it survives renames, moves between files and a colleague opening the same code.
  • Give library code its own colour. Includes are listed, and the headers behind them are recognised once you point the panel at your FreeBASIC installation.

Views & navigation

  • See the project in six views. Functions, Types, Groups, Files, Analysis and Settings, each grouped by colour.
  • Find what uses what. Callers and callees for a symbol, and where a type is instantiated.
  • Cut a list down to what is on screen. The scope filter answers "what is here right now" instead of "what exists somewhere".
  • Add things to Favourites. They get a section of their own in the Functions tab, and a star beside the code — in the gutter, in the overview ruler, in both, or nowhere.

Code intelligence

  • Read a symbol without leaving the file. Hover shows what it is, which group it is in, and who uses it.
  • Move a symbol to another group from the hover card.
  • Know which overload your call binds to.
  • See callers above every function — a CodeLens. Each caller's name is a clickable link that jumps straight to the call site. The group name is clickable too — it opens the Functions tab focused on that symbol.
  • Be told about unresolved names — but not about the library's. Header libraries are filtered away, and library code is not held against you.

Opening a project

Open a FreeBASIC project in VS Code and the panel is there — no setup files, no user name of its own, nothing to configure first.

The first time you open a project, a file for your groups and favourites is created for you silently, so the panel is usable the moment the project opens.

Your own code stays untouched: the panel reads your files where they are and writes only its own user file beside them.

What the panel sees

The panel lists what the project contains, grouped by colour: functions, subs, macros, types and enums, the modules they live in, and the libraries those modules include.

The include lines are listed in the Files view, so you can see at a glance what your project pulls in — and once you point the panel at your FreeBASIC installation, the headers behind those includes are recognised too.

The panel and the editor come from the same analysis, so they cannot disagree. The scope filter cuts a list down to the files actually visible on screen — (27/28) is how much of the project is in view right now.

Colour groups

You name the groups. A symbol belongs to one, the group has one colour, and that colour follows the symbol into the editor, into its hover card and into the panel. Assign a symbol once — there is nothing to keep in step afterwards.

Groups are yours to name: Library, Own_code, Interface, Needs_review. Names take letters, digits and underscores — a space is not allowed. Nothing is tied to any part of the language.

Creating a group

  1. Open the Groups tab in the panel.
  2. Press the + button. A form opens with a name field, a colour swatch that already holds a colour, and two buttons. The swatch is a button too — you do not have to accept the colour you are given.
  3. Click the swatch. The colour picker opens: a Saturation slider, and a grid of colours drawn at that saturation. Click a colour and the swatch takes it.
  4. Type a name and press Add. Until the name is filled in, Add stays greyed out. If the name is already in use, the form says so and refuses — you never end up with two groups of one name.

Choosing the colour

The picker works in HSL: the slider sets how strong the colour is, the grid sets the hue and how light it is. Move the slider and the whole grid redraws, so you can walk from muted to vivid without leaving the picker. To change a group that already exists, click its colour square in the list — the same picker opens.

Functions in a group

What a group's functions and subs look like — in the panel and in the editor, which are two views of the same analysis and therefore cannot disagree.

In the panel

Each group is a row of its own: the colour dot, the name, and the symbol counts — F: functions, S: subs, M: macros, T: types, E: enums. A Not used badge marks a group no code refers to yet, and a checkbox switches its colour off without touching its members.

Under the group header, its functions and subs as rows — each name drawn in the group's colour, each row expandable into Callers from N places and the functions it calls, every one of those in its own group's colour. Clicking a caller jumps straight to that call site.

A ball in the left margin shows where the definition lives: a bright ball means it is in the active editor — the one you are editing — and a dim grey ball means it is in any of the other visible editors, the ones actually shown on screen. A file merely open in a background tab gets no ball, and no ball means the definition is in none of the visible editors. The Types tab uses the same marker.

engine.bas — the one you are editing
Sub WorldSetup() '@a.Engine.me End Sub Sub LoadLevel() '@a.Engine.me End Sub
enemies.bas — visible beside it
Sub SpawnEnemy() '@a.Engine.me End Sub
Engine F: 3
WorldSetup
LoadLevel
SpawnEnemy

All three functions belong to the Engine group, so every name is blue. The ball answers a different question: where the definition lives. The two defined in the active editor get the bright ball; the one in the visible-but-not-active editor gets the dim grey one. A file only open in a background tab would get no ball at all, and in active file only mode the dim row would be filtered out entirely. Together the two marks tell you both who owns the name and whether it is on screen right now.

  • A ⭐ marks a favourite.
  • Right-click → add to Favourites or move to another group; Ctrl+Click selects many rows for a batch move.
  • Drag a group to reorder; the order is kept between sessions, enabled groups sort first, and Ungrouped is always at the bottom. While you search, empty groups drop out of the list.

Functions you have not put in any group are not lost: they live in the Ungrouped holding group — which is also the quickest way to see what is still unaccounted for.

In the editor

The same colour, on the definition and on every place the name is called: the symbol takes its group's colour straight away, and the group itself rides along in an ordinary comment at the end of the definition line — which is what keeps the membership through a rename, a move between files and a colleague opening the same project.

' Engine group (blue), Player group (orange), Enemy group (red)
Sub WorldSetup()                 '@a.Engine.me
    PlayerSpawn()                    ' Called: drawn in Player's orange
    EnemyClear()                     ' Called: drawn in Enemy's red
End Sub

The definition is blue because it is in Engine; the two calls are orange and red because those names belong to other groups. One function, three colours — each one answering "whose is this name".

Inherited groups

A group put on a Type or an Enum is inherited by everything declared with it: tag the type once, and its instances are drawn in that colour. The Types view marks those rows (I) Group — the colour is inherited, not owned, and the variable itself carries no tag.

An instance with a tag of its own keeps it. The type's group does not apply to that one as well: two groups on a single line would be two answers, and the colour already shows the one you chose. A common or extern variable declared in another module follows that declaration's group instead — one variable is the more specific statement.

' One type, one group
Type Vec2                        '@a.Engine.me
    x As Single
    y As Single
End Type

Dim Shared gTargetPos As Vec2
gTargetPos.x = 5                ' Every gTargetPos reference is drawn in the colour of Vec2's group.
' One enum, one group
Enum ShapeKind                   '@a.Engine.me
    SK_Circle = 1
    SK_Rectangle = 2
    SK_Polygon = 3
End Enum

Dim Shared gShape As ShapeKind
gShape = ShapeKind.SK_Circle   ' Every gShape reference is drawn in the colour of ShapeKind's group.

A group can be switched off without being deleted. It stops colouring and leaves the panel, but it is still there.

Instance colours

An instance of a type or an enum does not have to follow the colour of the group its type is in. Put the instance in its own group and it takes that colour instead — useful when one variable of a type matters to you and the rest do not.

' One type, three groups
Type Vec2                        '@a.Engine.me
    x As Single
    y As Single
End Type

Dim Shared gTargetPos As Vec2    '@a.Enemy.me
Dim Shared gPlayerPos As Vec2    '@a.Player.me
gTargetPos.x = 5
gPlayerPos.x = 5
' One enum, three groups
Enum ShapeKind                   '@a.Engine.me
    SK_Circle = 1
    SK_Rectangle = 2
    SK_Polygon = 3
End Enum

Dim Shared gShape As ShapeKind     '@a.Enemy.me
Dim Shared gKind As ShapeKind      '@a.Player.me
gShape = ShapeKind.SK_Circle
gKind = ShapeKind.SK_Rectangle

The colour also respects the symbol's real scope. A Dim Shared belongs to its own module, so its colour appears only there — another module naming the same word gets no colour, because that symbol is not visible to it. A Common Shared is the opposite: it is one variable every module shares, so its colour shows up in every module that uses it. Seeing the colour in a file tells you the symbol is really in scope in that file.

The same rule works inside a module. A variable declared outside a function keeps its colour inside every function that uses it — the scope reaches in, so the colour does too. A variable born inside a function is coloured only while that scope lasts: the colour stops at the end of the function and does not leak out. Loops and other nested blocks follow the same rule — the colour marks exactly the region the variable lives in.

' The colour marks exactly where the variable is in scope
Dim Shared gPlayerPos As Vec2      '@a.Player.me — orange for the whole module

Sub MovePlayer()
    Dim tmp As Vec2                   ' local: takes Vec2's blue, this Sub only
    gPlayerPos.x += tmp.x             ' scope reaches in → still orange here
End Sub                                ' tmp's colour ends here — it does not leak out

Nothing disappears if you have not classified it. An instance with no group takes the colour of the group its type is in; if the type is in no group either, the type and its ungrouped instances are drawn in the editor's normal text colour.

The six views

Functions — everything callable, grouped by colour, with callers and callees per symbol. Types — your types and enums, opened into their instances and members. Groups — where the colour groups are created, renamed, recoloured, reordered and switched off. Files — the modules in the project and the libraries they include. Analysis — which files carry the work and which symbols everything leans on. Settings — everything configurable, which is also where the panel opens.

Scope filter

The lists are big, because real projects are. Cut them down to the file you have open, or to the files actually visible on screen, so the panel answers "what is here right now" instead of "what exists somewhere".

When a list comes up empty it says why: nothing in this file, nothing matching your search, nothing in this category. A blank list with no explanation is worse than no list.

Hover

Hovering a symbol shows what it is, which group it belongs to, and who uses it. You can move the symbol to a different group straight from the hover card, without leaving the file you are reading.

Resolving follows scope. If a local variable shadows a module-level one of the same name, hover, colouring and group changes all describe the symbol you are actually pointing at.

Overload resolution

When a project uses overloaded functions, the editor works out which one your call binds to and shows you. Literals, local and module-level variables, expression results, conversion functions, type aliases and object member calls are all taken into account.

Without that, the answer would just be the first definition in the list — which is wrong exactly when the definitions are in a different order from what you expected.

Favourites

Mark the functions you keep coming back to. They are starred beside the code in the editor, so the two or three you actually work with are findable at a glance in a file you have not opened in months.

Favourites get a section of their own in the Functions tab, grouped into collapsible per-kind sections — Functions, Subs, Macros, Types, Enums, Instances — each with its own expander. Every favourite is tagged with its kind, so a starred type never hides among starred functions.

You can sort by name, by group or by kind, and filter to show only Functions/Subs or everything. Each kind section takes a right-click for batch work: remove everything in the section, or set everything in it to one group in a single move.

The star can sit in the editor gutter, in the overview ruler beside the scrollbar, in both, or nowhere — your choice in Settings.

Category filters

The top row of the Functions tab carries five small icon toggles: Functions, Subs, Macros, Public and Private. They answer a different question from the colour groups: not "which part of the project" but "what kind of thing is this".

The two axes are independent and combine as an AND. Every symbol has a kind and a visibility, so a row shows when its kind is on and its visibility is on. That opens combinations a single choice could never express: all public functions and subs at once; every private symbol of every kind; all three kinds with only the publics.

Two rules worth knowing

  • At least one of Public/Private stays on. Clicking the last one off does nothing — a filter with both visibilities off would hide everything for no reason. When both are on, either one may be switched off.
  • Macros ignore the visibility axis. A macro has no Public or Private concept, so it is shown only while the visibility axis is fully open. "Private only" would be claiming the macro is private, and that would be a lie.
  • Declares belong to the unfiltered view. A Declare line carries no metadata of its own — the extension finds its alias from the definition in another file — so it appears when all three kinds are on, and steps out of narrower categories.

The search box combines with the toggles as another AND: the text searches inside the categories you left on. The active toggles are drawn in the badge colour, the inactive ones in grey, and the choice is kept between sessions.

The Types view

Types and enums each get their own expander with a count — and each type or enum opens into its instances: every Dim x As T that was declared with it, indented underneath. Instances start collapsed, so a type with thirty variables costs one row.

  • Same name in several files collapses. One name (N) row stands for them all; opening it lists the individual files.
  • (I) means inherited. An instance with no tag of its own is already drawn in its type's group colour — the (I) marker is what makes that colour legible and says the instance itself is not in the group. Hover the (I) to see which group is meant. An instance with its own group shows only that one.
  • A bright dot marks the active editor, a dim grey one any of the other visible editors — a background tab gets no dot. The dot in the left margin means "this definition lives in one of the editors you can see" — for types, enums and instances alike. It is a location fact, not a visibility one: an instance in the active file keeps its bright dot even when its type lives elsewhere.
  • Name rows are shaded like the group headers in the Functions tab, so a type always reads as the head of what follows it.

The expander you touched last keeps its marker, so you can find your way back after scrolling — even if you closed it again. The gold row highlight means something else: "you are here", from a hover jump or a click.

Search

Both list tabs search by name as you type, and both combine the search with their filter as an AND — a type defined in another file stays hidden by active file only even when the search finds it.

Types search matches the whole row

Not just type names: searching an instance or a member name finds its parent and shows only the children that matched. When the type's own name matches, the row is shown whole — instances and members intact — because you are looking for that type, not for its members.

Small rules that matter

  • Case-insensitive.
  • Esc clears the box.
  • Neither the search nor the filter is stored between sessions: the tab must never open narrowed without telling you why.
  • A jump from a hover wins over the narrowing: if the target is hidden, both the search and the filter switch themselves off — visibly, in the top row — so the target is actually reachable. A target that is already visible leaves the narrowing alone.

Empty lists

A blank list with no explanation is worse than no list. When a list comes up empty it says why — and the message names the filter that caused it:

  • No matches for "x" — the search found nothing. With the category filters on, it is the search text that is named, because that is what narrowed last.
  • No types from the active file / from the visible files — the wording follows the actual scope mode. An old hardcoded "active file" would be a lie when the list is cut to open files.
  • No functions in used groups — everything visible belongs to groups that are switched off.
  • No functions in this category — the category filter is the reason, and the list says so rather than pretending the project is empty.

The Types tab has two lists, so an empty message names its section too — "No enums match \"x\"" under a visible type hit would otherwise read as the whole tab having found nothing.

Diagnostics

Unresolved names are reported — but the ones coming from FreeBASIC's own header libraries are filtered away, and library code is not held against you. Point the extension at your FreeBASIC installation and the headers behind your includes are recognised too, so a type name that lives in a header is not an unknown symbol.

What reaches you is meant to be yours to fix.

CodeLens

Above every function definition sits a line of links. It starts with Group: <name> — click it and the Functions tab opens, focused on that group and that function — followed by Callers: and each caller's name as its own clickable jump straight to the call site.

When a function has more than ten callers, the rest collapse behind +N more…, which opens a searchable list you can filter by typing. A function with no callers says so instead of showing an empty line.

The CodeLens can be switched off in Settings (editor.codeLens) if you would rather keep the space above your definitions.

Multi-user

Several people can work on the same code with their own groups, colours and favourites, without interfering with each other. Each user's settings live in their own file in the project folder — the first time you open a project, one is created for you silently, so there is nothing to configure.

The group markers in the code carry a user identity, which is what makes this work: everyone sees and edits only their own groups and favourites, even on identical code. A group survives a rename, a move between files and a colleague opening the same project — the tag is what carries it, and the tag is yours.

This costs nothing when working alone — it is the same mechanism, just with one identity in play.

Settings

Everything configurable lives in the panel's own Settings tab, and can be stored at User or Workspace scope:

  • Decoration colour — the colour and transparency of the marker highlights in the editor (decorationColor).
  • Hover on/off — whether the hover card is shown at all.
  • Block background and border alpha — how strong the highlight blocks behind decorated ranges are drawn.
  • CodeLens — the caller line above function definitions (editor.codeLens, on by default).
  • Your user file — the settings file the groups and favourites are written to, also where the define location of a group points when you click it.

The extension needs no setup files and no user name of its own: open a FreeBASIC project and the panel is there.

Build status

The generated declaration file goes stale the moment you change a signature. The panel knows this and keeps the state visible instead of letting you build against a file that no longer matches your code:

  • An edit marks the build stale. The compile button carries the marker in its own name — not a separate box somewhere — so the button you are about to press is the one telling you.
  • A failed regeneration is reported. If writing the generated file fails, you are told; there is no silent compile against an old file.
  • A failed compile does not run the old executable. When the compiler reports errors, the previous .exe is left alone — running it would be yesterday's program with today's name.
  • Line numbers stay true. The compile-time copies keep every line on its own line number, so an error the compiler reports on line 6 is on line 6 of your own file.

Declarations & build

Every module-level function and sub gets a declaration written into a single file, and the compiler is told to read that file first — so no module ever calls something the compiler has not been told about, and reordering your files stops breaking anything.

The same one-line invocation builds the project. Your own code stays untouched; the generated file lives beside it.

The Files tab

Which modules take part in the build, and in what order, is yours to decide there. Every module in the project has a checkbox: the ticked ones go to the compiler and the unticked ones are left out, so a half-finished file does not have to stop the build.

Drag a row to move it. The order is the execution order: the lowest checked file runs first, and the topmost checked file runs last. The topmost file is the main file — the one the executable is named after.

Automation

Everything the compiler needs to know about your project goes into one file, generated.bi, which is handed to the compiler ahead of your modules. You never write it and you never include it by hand.

The file is written in this order:

  1. Comment lines
  2. #include lines
  3. #define lines
  4. Const lines
  5. Enum blocks
  6. Type blocks
  7. Union blocks
  8. Declare lines

The comment lines at the top say what the file is and how it is meant to be compiled. They are comments, so the compiler ignores them — they are there for whoever opens the file.

The include lines are copied from your modules, once each. once is added where it is missing, and a library include keeps the tag that gives it its own colour in the panel.

The defines, consts, enums, types and unions are lifted out of the modules that declare them, tags and all, and sorted by what depends on what — a type that uses a const comes after it. The order above is where each kind starts, not a rule the result has to keep.

Declares are written for every module-level function and sub, including the member procedures of a type. A Declare line you wrote yourself in a module is never copied here: it stays where it is, and the file gets no second one.

What is not in it: no variable declarations, no Sub or Function bodies, and nothing you wrote as an initialisation. Those stay in your own files, where you wrote them.

generated.bi (written for you) 
' .bi generator output
' Includes, consts, defines, enums, types/unions and Declare lines:
' no variables, no bodies.

#include once "SDL3/SDL.bi" '@e.SDL3

type Vec2 '@a.Engine.me
    x As Single
    y As Single
end type

Declare Sub WorldSetup()
Declare Function FieldArea() As Single

The compile-time copies

A #define, Type, Enum or Union cannot appear twice — the compiler stops with error 4. Since generated.bi is included into every module, a lifted block has to be absent from the module it came from.

So for the duration of the compile each file that contributed a lifted block gets a copy beside it, in the same folder, named <module>.bi_temp.bas.

What is taken out of that copy is what the compiler will not accept twice: every #define, Enum, Type and Union block that came out of that module. Each of their lines is replaced by a blank line, so the file keeps its length and every line below stays on its own line number.

Const lines are left where they are: a duplicate Const is legal, and the module's own line is what its own code uses. Declare lines are not involved either — the generated file only gets a Declare where the module does not already have one. A file that contributed nothing is not copied at all.

01_types.bas — your file

Type Vec2
    x As Single
    y As Single
End Type

Public Sub WorldSetup()
    gPlayField.w = 800.0
End Sub

01_types.bi_temp.bas — what the compiler gets






Public Sub WorldSetup()
    gPlayField.w = 800.0
End Sub

The copy is the same file, four lines emptier and not one line shorter. That is the whole point: an error the compiler reports on line 6 of the copy is reported to you on line 6 of your own file.

The copies are always deleted when the compile finishes. The .bi_temp.bas name is what keeps them out of the module list and out of the analysis while they exist, and what stops anything mistaking them for your sources.

The command

Your checked files go to the compiler in the order you arranged them in the panel, with the generated file first and the output flag last:

fbc -include generated.bi main.bas 01_types.bas -x main.exe

The executable is named after the first checked file, not after a copy — so it is called what you think your program is called.
